API

Application Programming Interface
♡
Plain English
A defined way for two systems to communicate.
Think of it like a waiter carrying a request to the kitchen and bringing the response back.

At work
“We'll expose an API for customer details.”
Meaning: another system can request customer information through an agreed contract.
BA Lens

Ask: What goes in? What comes back? What happens if it fails?

Don't confuse: API = how systems interact · Database = where data lives
Remember: An API is the agreed doorway. One system asks; another responds.
K

Kafka

Event streaming platform
♡
Plain English
A system for publishing events so other systems can react to them.
Think of it like a shared noticeboard: one team posts; interested teams pick it up.
See how it works
Order Service → Kafka Topic
event published ↓
PaymentNotificationAnalytics
One system publishes. Multiple systems can listen independently.
At work
“Publish the order-created event to Kafka.”
Meaning: emit an event so downstream systems can react without a direct call.
BA Lens

Ask: What creates the event? Who consumes it? What happens on retry or duplication?

Don't confuse: Kafka = event stream · API = direct request/response
Remember: Kafka helps systems react to events without every system calling every other system directly.
μ

Microservices

Independent services by business capability
♡
Plain English
An application split into smaller services, each responsible for a specific capability.
Think of it like a food court: separate counters, each owning one job.
See how it works
Customer journey
↓ routed across services
CustomerOrderPaymentNotification
One customer journey can cross several independently owned services.
At work
“Payment is handled by a separate microservice.”
Meaning: payment logic lives in its own independently managed service.
BA Lens

Ask: Which service owns the rule? What depends on it? What if it is unavailable?

Don't confuse: microservice = responsibility boundary · not simply “small code”
Remember: The useful question isn't “how small is it?” It's “what capability does this service own?”
ID

Authentication vs Authorization

Identity vs permission
♡
Plain English
Authentication proves who you are. Authorization decides what you're allowed to do.
See the difference
Authentication“Who are you?”
Login · password · MFA
→
Authorization“What can you do?”
Role · permission · access
Identity first. Permission second.
At work
“The user is authenticated but isn't authorized to approve payments.”
Meaning: we know who they are, but their role does not allow that action.
BA Lens

Ask: What roles exist? What can each role see and do? What happens when access is denied?

Don't confuse: login ≠ permission
Remember: Authentication gets you through the front door. Authorization decides which rooms you can enter.
CI

CI/CD

Continuous Integration / Continuous Delivery or Deployment
♡
Plain English
Automation that builds, tests, and moves code toward release.
Think of it like a conveyor belt that checks every change before it moves forward.
See how it works
Code
Build
Test
Deploy
A change progresses only when the required checks pass.
At work
“The CI/CD pipeline failed.”
Meaning: an automated build, test, delivery, or deployment step did not complete successfully.
BA Lens

Ask: Which stage failed? Which environment? Was the change deployed — and was it released to users?

Don't confuse: deployed ≠ released to users
Remember: CI/CD is the automated path a code change takes from commit toward production.
